# Webhooks

The Course Catalog API delivers signed webhook events to subscriber-owned HTTPS
endpoints. This document defines the event envelope, payload fields, signature
scheme, replay protection, retry policy, and idempotency rules. The machine
readable contract is in [`openapi.yaml`](../openapi.yaml); the matching Zod
schemas are in [`src/schemas/webhook.ts`](../src/schemas/webhook.ts).

## Event types

| Event | Version | Emitted when |
| --- | --- | --- |
| `course.published` | `1.0` | A course transitions to `published`. |

Only `course.published` is currently supported. Event `type` and `version`
identify the payload schema. Adding or changing fields in a breaking way
requires a new version. Subscribers should acknowledge events they do not
handle with a 2xx response and ignore them.

## Creating a subscription

Create a subscription with `POST /v1/webhooks/subscriptions` using a
`catalog_admin` or `service` token. The URL must use HTTPS. The response
contains a one-time `signingSecret`; store it in a secret manager. The secret is
never returned again.

```bash
curl -s -X POST "https://api.course-catalog.dev/v1/webhooks/subscriptions" \
  -H "Authorization: Bearer $CATALOG_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://lms.example.com/webhooks/catalog",
    "events": ["course.published"],
    "description": "LMS synchronization"
  }'
```

```json
{
  "data": {
    "id": "whs_01J9ZK7C3D4E5F6G7H8J9K0M1N",
    "url": "https://lms.example.com/webhooks/catalog",
    "events": ["course.published"],
    "status": "active",
    "description": "LMS synchronization",
    "createdAt": "2026-03-01T15:00:00Z",
    "updatedAt": "2026-03-01T15:00:00Z",
    "signingSecret": "whsec_example_do_not_use_6f1c9a2e7b4d8f0a"
  }
}
```

The `signingSecret` above is a documentation placeholder, not a usable secret.

## Event envelope

Every delivery body is a JSON object with these top-level fields:

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Event ID, prefixed with `evt_`. Stable across all delivery retries. Use it as the idempotency key. |
| `type` | string | Event type. Currently `course.published`. |
| `version` | string | Event schema version. Currently `1.0`. |
| `occurredAt` | string | RFC 3339 timestamp of when the event occurred. |
| `data` | object | Event-specific payload. |

### `course.published` data

| Field | Type | Description |
| --- | --- | --- |
| `course` | object | The published course resource, matching the `Course` schema. |
| `instructors` | array | Full instructor resources referenced by `course.instructorIds`. |
| `prerequisites` | array | Current prerequisite rules for the course, matching `PrerequisiteRule`. |
| `enrichment` | object | Advisory content generated by Workers AI or the deterministic fallback. |
| `enrichment.summary` | string | Short plain-text summary of the course. |
| `enrichment.tags` | string[] | Short topic tags. |
| `enrichment.suggestedPrerequisites` | string[] | Suggested course IDs, prefixed with `crs_`. Advisory only. |
| `enrichment.source` | string | `ai` when Workers AI produced the enrichment, `fallback` when the deterministic fallback was used. |

The canonical course, instructor, and prerequisite data is in `course`,
`instructors`, and `prerequisites`. Never treat `enrichment` as authoritative
for eligibility or catalog policy.

## Delivery headers

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json; charset=utf-8` |
| `User-Agent` | `CourseCatalog-Webhooks/1.0` |
| `X-Catalog-Event` | Event type, for example `course.published` |
| `X-Catalog-Event-Id` | Event ID, matching the envelope `id` |
| `X-Catalog-Delivery` | Delivery attempt ID, prefixed with `whd_` |
| `X-Catalog-Signature` | Signature header described below |

Each retry creates a new `X-Catalog-Delivery` value but preserves the same
`X-Catalog-Event-Id`. The request body is byte-for-byte identical across
retries of the same event.

## Signature scheme

The `X-Catalog-Signature` header has the form:

```text
t=<unix>,v1=<hex hmac-sha256 of t.body>
```

- `t` is the Unix timestamp in seconds when the delivery was signed.
- `v1` is the lowercase hexadecimal HMAC-SHA256 digest of the ASCII string
  `t` + `.` + the raw request body bytes.
- The HMAC key is the subscription's signing secret, encoded as UTF-8.
- The raw body is signed exactly as sent. Do not parse and re-serialize JSON
  before verification.

Example:

```text
t=1772377200,v1=8f14e45fceea167a5a36dedd4bea2543f0c2a1d3e4b5c6d7e8f90123456789ab
```

For version 1.0, exactly one `v1` value is sent. Verifiers should parse
comma-separated `key=value` pairs, require `t` and `v1`, and reject malformed
values. Future signature versions may add additional fields; this does not
change the meaning of `v1`.

### Replay window

Reject a delivery when the signed timestamp is more than **5 minutes** away from
the receiver's current clock:

```text
abs(nowSeconds - t) > 300  =>  reject
```

Use the signed `t`, not timestamps inside the JSON body, for replay checks.
Also deduplicate by event ID. A delivery can be retried for up to roughly two
hours, so retain event IDs for at least seven days. Reject missing, malformed,
or stale timestamps before processing the event.

### Verification in a Worker

The Workers runtime exposes the standard Web Crypto API as `crypto.subtle`.
Verify with the raw body and the subscription signing secret:

```ts
const encoder = new TextEncoder();

export async function verifyCatalogSignature(
  rawBody: string,
  signatureHeader: string,
  signingSecret: string,
  nowSeconds = Math.floor(Date.now() / 1000),
): Promise<boolean> {
  const parts = signatureHeader.split(",");
  const timestampPart = parts.find((part) => part.startsWith("t="));
  const signaturePart = parts.find((part) => part.startsWith("v1="));

  if (!timestampPart || !signaturePart) {
    return false;
  }

  const timestamp = Number(timestampPart.slice(2));
  const providedHex = signaturePart.slice(3);

  if (!Number.isInteger(timestamp)) {
    return false;
  }
  if (Math.abs(nowSeconds - timestamp) > 300) {
    return false;
  }
  if (!/^[a-f0-9]{64}$/.test(providedHex)) {
    return false;
  }

  const key = await crypto.subtle.importKey(
    "raw",
    encoder.encode(signingSecret),
    { name: "HMAC", hash: "SHA-256" },
    false,
    ["verify"],
  );

  return crypto.subtle.verify(
    "HMAC",
    key,
    hexToBytes(providedHex),
    encoder.encode(`${timestamp}.${rawBody}`),
  );
}

function hexToBytes(hex: string): Uint8Array {
  const bytes = new Uint8Array(hex.length / 2);
  for (let index = 0; index < bytes.length; index += 1) {
    bytes[index] = Number.parseInt(
      hex.slice(index * 2, index * 2 + 2),
      16,
    );
  }
  return bytes;
}
```

In the request handler, read the body once as text, verify the signature, then
parse the JSON:

```ts
const rawBody = await request.text();
const signature = request.headers.get("X-Catalog-Signature") ?? "";

if (!(await verifyCatalogSignature(rawBody, signature, signingSecret))) {
  return new Response("invalid signature", { status: 401 });
}

const event = JSON.parse(rawBody);
```

If you compare digests manually instead of using `crypto.subtle.verify`, use a
constant-time comparison such as the Workers `crypto.subtle.timingSafeEqual`
extension or an equivalent implementation.

## Delivery and retry policy

Deliveries are **at least once**. Ordering is not guaranteed. The same event
can arrive more than once, including on different delivery IDs.

- Success is any HTTP `2xx` response received within **10 seconds**.
- Redirects are not followed. A `3xx` response is a failure.
- Network errors, timeouts, `408 Request Timeout`, `429 Too Many Requests`, and
  `5xx` responses are retried.
- Other `4xx` responses are not retried.
- A `410 Gone` response disables the subscription immediately.
- Maximum of **6 attempts** per event and subscription.
- Exponential backoff with jitter. Attempt 1 is immediate. Later attempts use
  `min(30 * 4^(attempt - 2), 7200)` seconds, plus or minus 20% jitter.

| Attempt | Approximate delay before the attempt |
| --- | --- |
| 1 | immediate |
| 2 | 30 seconds |
| 3 | 2 minutes |
| 4 | 8 minutes |
| 5 | 32 minutes |
| 6 | 2 hours |

After the sixth failed attempt, the delivery is marked `exhausted` and no more
attempts are made. Delivery records are available through
`GET /v1/webhooks/deliveries` to `catalog_admin` and `service` callers, with
filters for subscription, event, status, and event type.

Delivery statuses:

| Status | Meaning |
| --- | --- |
| `pending` | Waiting for the first attempt or a scheduled retry. |
| `delivered` | A 2xx response was received. |
| `failed` | The most recent attempt failed and a retry is scheduled. |
| `exhausted` | All six attempts failed; no further retries. |

Respond with a 2xx only after you have durably accepted the event. For slow
processing, persist the event and return 2xx quickly, then process it
asynchronously. Do not return 2xx before you have verified the signature and
stored the event.

## Idempotency by event ID

Use the envelope `id` (also sent as `X-Catalog-Event-Id`) as the idempotency
key:

1. Verify the signature and replay window.
2. Check whether the event ID has already been processed.
3. If it is new, atomically record the event ID and process the event.
4. If it already exists, return a 2xx response without repeating side effects.

Retries preserve the event ID. The `X-Catalog-Delivery` value changes per
attempt and must not be used for deduplication. Retain processed event IDs for
at least seven days; longer retention is safer.

## Subscription endpoint requirements

- Use a public HTTPS endpoint with a valid certificate.
- Do not use private, loopback, link-local, or metadata-service addresses.
- Verify signatures and timestamps before parsing or acting on the body.
- Keep the signing secret in a secret manager, not in source control.
- Return 2xx promptly after durable acceptance.
- Monitor `GET /v1/webhooks/deliveries` for `failed` and `exhausted` states.
